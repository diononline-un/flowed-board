- 2026-09-21 — Capture consent gate runs *before* the daily-counter consumption (SPEC 9.1 lists the limit check first): users without consent never burn quota for calls that cannot happen; observable behavior is otherwise identical.
- 2026-09-21 — `POST /api/capture/parse` returns an additive `fallback: boolean` next to `items` (SPEC 9.1 names only `{items}`); the client needs the flag to show the SPEC-9.4 fallback hint.
- 2026-09-21 — Capture commit never auto-creates goals/habits from suggestions (M3 brief), although the SPEC-7 table says "Post-its/Ziele"; only exact-title matching against existing own rows.
- 2026-09-21 — Past dates in LLM answers are clamped to today (mechanism for SPEC 9.1 "nie in der Vergangenheit", which names none).
- 2026-09-21 — The capture input relies on the Sheet focus trap focusing the first input instead of the `autofocus` attribute (SPEC 8.1 wording kept functionally, a11y-linter-clean).
- 2026-09-21 — Habit window, counter and pace logic live in a new `src/lib/shared/habit.ts` instead of extending `progress.ts` (M4 brief allowed either): `progress.ts` is the SPEC-5.4 goal rule, habits are a separate SPEC-5.5 domain and the calendar grid helpers sit next to them in `shared/calendar.ts`.
- 2026-09-21 — `completedPeriods` counts finished weeks (or months) from `created_at` up to the last closed period and includes the running window in "Beste Woche/Bester Monat", so the value never sinks by skipping a period (P3/P7); the displayed "Wochen/Monate geschafft" only ever counts closed windows, which is what SPEC 5.5 asks for.
- 2026-09-21 — A `week`/`month` habit created in the past can still receive backdated tap logs (SPEC 5.5 only restricts future dates and the 60-day limit); only `range` habits reject days outside `[range_start, range_end]` with 422.
- 2026-09-21 — `DELETE /api/habits/:id` soft-deletes the habit and leaves its `habit_logs` rows untouched (restoring via `POST /api/habits/:id/restore` brings the counters back exactly; SPEC 7 says "archivieren (soft-delete)" and defines no log cascade).
- 2026-09-21 — `POST /api/habits/:id/logs` answers additions with 201, removals (`delta:-1`) with 200 and returns `{habit, log|null, dayCount, todayCount}` — the client needs the authoritative per-day count to reconcile the optimistic update (SPEC 7 names only "Log +1/−1").
- 2026-09-21 — The calendar keeps the shown window in client state and refetches `/api/postits?from,to` when the user navigates; the initial render still comes from `+page.server.ts` (SPEC 3.1), and out-of-range post-its are dropped so the client array cannot grow without bound while stepping through weeks.
- 2026-09-21 — The calendar defaults to the week view and switches to the month view only via the toggle (M4 brief: "Wochenansicht (Default)"); the `?view=month` query parameter is accepted for the first render.
- 2026-09-24 — The SPEC-5.7 due window never crosses midnight: `time + 6 h` is clipped to 24:00 for late slots, because both `entry_date` and `slot` belong to one calendar day (a 22:00 slot is due until midnight, not until 04:00 the next morning); a schedule with times but no weekday is rejected with 422 instead of silently never firing.
- 2026-09-24 — `JournalField.id` must match `^[A-Za-z0-9_-]{1,40}$`: the id is the JSON key of `values_json` and the DOM id of its input, so it stays attribute-safe (SPEC 5.7 only says "stabil").
- 2026-09-24 — Numeric values may arrive as strings (`"4"`), yes/no as `"true"`/`"1"` — they are normalized to number/boolean before storage; optional answers sent as empty strings are dropped, required ones rejected (422).
- 2026-09-24 — `POST /api/journal/entries` refuses a deactivated template (422) and an `entryDate` in the future (422): "Nachtragen" of SPEC 5.7 means today or earlier, and a deactivated template must not collect new answers.
- 2026-09-24 — `GET /api/journal/templates` returns the active set by default and adds deactivated templates with `?includeInactive=1` (mirrors `?archived=1` of habits); there is no DELETE for templates — SPEC 7 offers GET/POST/PATCH only, and AC14 keeps entries readable after deactivation.
- 2026-09-24 — Values of an entry are validated against its own `fields_snapshot`, not against the current template (AC14): editing a template cannot invalidate existing entries, and `PATCH /api/journal/entries/:id` merges the submitted values into the stored ones so partial edits stay valid.
- 2026-09-24 — `GET /api/journal/due` returns `{today, nowTime, items}` where items are `{template, slot}`; `today`/`nowTime` are additive to the SPEC-7 `{items}` shape and let the client show the server-computed day without recomputing the rule.
- 2026-09-24 — `/journal` loads the last 90 days of entries in `+page.server.ts` (`from`/`to` are API parameters, so widening the window is one number) and the entry sheet is a client-only overlay like the M2/M4 sheets.
- 2026-09-24 — The M6 award path (`src/lib/server/xp.ts`) writes `xp_events` itself instead of a pure `repo/xpEvents.ts` orchestration (SPEC 16 names `xp.ts` for "5.6-Logik" and the SPEC-5.6 table for the SQL); SQL stays in `repo/xpEvents.ts` and `repo/badges.ts`, and the service only calls them.
- 2026-09-24 — `POST /api/auth/register` seeds the SPEC-8.7 content right away and `POST /api/onboarding/complete` seeds again; `seedUserContent` is idempotent (each block only fills what is missing), which is what makes the complete skip of SPEC 8.6 end in a usable board (AC15) while SPEC 8.6 still says the completion loads the seed.
- 2026-09-24 — `is_example` drives exactly one thing: a quiet "Beispiel" chip on post-it/goal/habit (`ExampleChip.svelte`). Seeded rows are ordinary content — editable, deletable, part of every count and badge rule.
- 2026-09-24 — Badge definitions and thresholds live in `src/lib/shared/badges.ts`, `user_badges` stores only `(badge_id, earned_at)`; badges are evaluated from the current rows after every relevant event, so no counter can drift and a badge can never be taken away (P7).
- 2026-09-24 — `keeper` counts distinct weeks in which a habit reached its target, weeks reported by their own start date and counted from `created_at` up to the last closed week (the same clipping as "Wochen geschafft", SPEC 5.5), so the two displays cannot disagree.
- 2026-09-24 — XP for a goal, a key result or a capture is only awarded on the *crossing* (goal status → done, key-result `current >= target`, a new batch id); a key result that starts out complete, a repeated cleanup run or a re-opened goal awards nothing, because the event ref_id already exists or the state never changed.
- 2026-09-24 — `POST /api/postits/cleanup` awards `postit_done` for the post-its the sheet completes and always runs the `tidy_up` badge check; the `cleanup` trigger is the one fact that is not derivable from the rows itself (`gatherBadgeFacts(userId, today, weekStart, trigger)`).
- 2026-09-24 — Mutations carry an additive `xp` object (`{gained, total, level, levelName, levelUp, newBadges}`) next to the changed resource; the key is omitted entirely when nothing was gained, so pre-M6 response shapes stay valid (SPEC 7: mutations return the resource). The client shows the toasts only when `prefs.gamification` is on — the server always records the XP (SPEC 5.6).
- 2026-09-24 — The XP bar, the level chip and the badge grid live in the settings section "Gamification" (the brief allowed "Settings oder eigener Bereich in /plans"); the sidebar shows a compact level chip, and both are hidden when `prefs.gamification` is off. There is no leaderboard and no comparison between users (P7) — `user_badges`/`xp_events` are only ever read for one userId.
- 2026-09-24 — The Quick-Capture flow moved into `CaptureFlow.svelte`; `CaptureSheet` wraps it in the Sheet (closing itself after a commit), the onboarding step 2 embeds it and resets it via a `resetKey` prop instead of mounting a second implementation.
- 2026-09-24 — `GET /api/summary` returns `{today, weekStart, weekEnd, dueToday, week:{total,done}, xp, newBadges}`; "heute fällig" counts open post-its dated today **or earlier** (overdue work still waits), and `newBadges` lists the badges earned on the current day (badge grid = settings page).
- 2026-09-24 — The onboarding guard sits in `(app)/+layout.server.ts` and excludes `/onboarding` in both directions (no `onboarding_done_at` → redirect to `/onboarding`; set → redirect away from it), while `(app)/onboarding/+page.server.ts` repeats the redirect to `/plans`; the completion ends in a full `window.location` navigation so the fresh layout data carries the stamped value (AC16).
- 2026-09-24 (Fix) — `xpAtLevel(L) = 30 * (L−1)²` (die Schwelle, an der `levelFor` umschaltet) statt der Summe der Bänder: die Summe widersprach der Level-Formel ab Level 3 (negatives `intoLevel`, negative Balkenbreite, falsches `toNextLevel`); `xpToNextLevel` ist auf 0 geklemmt.
- 2026-09-24 (Fix) — `XpResponse` ist flach und trägt `total`/`level`/`levelName` auch bei `gained: 0` (Badges ohne eigene XP wie `goal_setter`/`tidy_up`), `withXp` übernimmt sie unverändert; clientseitig setzt `applyXp` den Store zusätzlich nur bei `gained > 0 && total > 0`, damit eine Badge-Antwort die Anzeige nie zurücksetzen kann. Der Payload-Typ `XpResponsePayload` liegt in `shared/xp.ts` (eine Definition für Server und Client).
- 2026-09-24 (Fix 2) — `XpProgress` trennt Level-Start, Level-Breite und Restmenge: `xpAtLevel(L) = 30*(L−1)²` (Start), `xpBandWidth(L) = 30*(2L−1)` (Breite), `toNextLevel = xpAtLevel(L+1) − total`, `ratio = intoLevel / bandWidth`; das `30 * level²` aus SPEC 5.6 ist die kumulative Level-Schwelle (= `xpAtLevel(L+1)`), nicht die fehlende Restmenge, und der Balken misst die Level-Breite statt der Schwelle.
